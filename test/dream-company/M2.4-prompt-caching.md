# M2.4 — Prompt caching for Dream Company: investigation & decision

**Decision: NOT worth implementing.** Evidence below. (AC allows "enable + measure" *or*
"justify why not" — this is the justification, logged so no one re-tries it.)

## Measured input sizes (real requests, model `claude-sonnet-4-6`)

| Step | Input tokens | Output tokens | vs Sonnet cache min (1024) |
|------|-------------:|--------------:|----------------------------|
| analyze  | ~571  | ~1000–1230 | **below min → cannot cache** |
| roles    | ~935–958 | ~1300 (10 roles) | **below min → cannot cache** |
| parse-cv | ~559  | ~180 | **below min → cannot cache** |
| roadmap  | ~2202 | ~2070 | above min, but see below |

Anthropic prompt caching requires the cached **prefix** to be **≥1024 tokens** (Sonnet) and to
be **reused** across requests. Source: repo's own `docs/INTERVIEW_PREP_WORKFLOW.md` /
`CLAUDE.md` ("Sonnet 4.0 caching constraints: 1024-token min prefix").

## Why it doesn't pay off

1. **3 of 4 steps are below the 1024-token minimum** (analyze 571, roles 955, parse-cv 559).
   Their *entire* input is smaller than the smallest cacheable prefix — caching is impossible,
   not just unhelpful.
2. **roadmap (2202) clears the minimum, but has no cacheable prefix.** Its prompt interpolates
   the per-request profile / analysis / selected roles / live jobs **first**, and puts the large
   static instruction block (task + rules + schema) **last**. Caching only caches a *prefix*, so
   the static text — which sits at the end — can't be cached. The short intro before the dynamic
   data even interpolates `${analysis.marketLevel}`, so it isn't static either.
3. **No cross-request reuse.** Caching pays off when many requests share an identical prefix
   within the TTL (this is exactly why interview-prep caches: one session replays a 3500–5700
   token JD+CV prefix every turn). Dream Company runs each step **once per user**, and every
   user's profile differs — so there's no repeated prefix to hit.
4. **Latency is output-bound, not input-bound.** Output tokens (≈1300–2400) exceed input tokens
   at every step, and output generation is the slow part. Caching only speeds up *input*
   processing, so even a perfect cache would not move the perceived-latency needle — which is the
   whole point of M2. Streaming (M2.1) addresses the actual bottleneck.

## If we wanted to force it (and why we still shouldn't)

We *could* restructure the roadmap prompt to front-load the static instructions as a ≥1024-token
cacheable prefix. But: the cost saved is ~1k input tokens ≈ $0.001/call (input is cheap), the
latency saved is negligible (input isn't the bottleneck), cross-user hit rate is ~0 at current
traffic, and it adds a silent-invalidation maintenance burden. Effort is better spent on M2.1.

## Recommendation

Skip caching. Revisit only if (a) traffic grows enough for same-profile bursts within the 5-min
TTL, or (b) prompts grow large enough that input processing becomes a real share of latency.
